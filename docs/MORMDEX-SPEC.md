# MORM 機密精算レイヤ 設計仕様書（SPEC）

**内部コードネーム**: MORMDEX（※サブブランドとして外部に名乗らない — MORM3原則②）
**バージョン**: v0.2.0（ドラフト・**ノンカストディ / コンセプト優先版**）
**日付**: 2026-08-06
**位置づけ**: MORM L1 上の「機密だが検証可能」な**自己保管型**入出金・精算レイヤ

> ⚠️ 本仕様は **プライバシー保護** と **自前チェーンMORMでの精算基盤** の2目的に限定。
> 「追跡回避」「資金源の秘匿」「他人資金の混合」を目的とした設計は**対象外・実装禁止**。

---

## 0. 設計判断（v0.1→v0.2の転換）

**決定：MORMのコンセプトを最優先する。** その帰結として設計を反転する。

| MORM原則 | 帰結 |
|---|---|
| 法人を持たない | **custodial 不可**（＝VASP登録が必要になる）→ **ノンカストディに転換** |
| サブブランドを作らない | 独立ブランド"MORMDEX"を名乗らない → **MORMの一機能**として実装 |
| 発明者と名乗らない／先行技術認知 | 既存プライバシー研究の上に建て、明示的に引用（§7） |

### 2本の越えてはいけない線
1. **custodial の壁**：資金を預かると法人＋暗号資産交換業登録が必須 → **資金を預からない**ことで回避
2. **mixer の壁（Tornado Cash 型）**：他人同士の資金を混ぜ入出金リンクを断つと、法人が無くても制裁・マネロン幇助の対象 → **他人資金を混合しない**ことで回避

> **一線**：*自分の自己保管資産の秘匿はOK。他人の資金の入出金リンクを断つ共有匿名プールはNG。*
> self-custody confidentiality を作り、anonymity mixing は作らない。

## 1. 何を作り、何を作らないか

**作る（✅）**
- ユーザーが**自分の鍵で自分の資産を保持**する非預かり型ウォレット/精算
- 残高・履歴を**第三者（公開エクスプローラ・他ユーザー）に晒さない**機密性
- 「台帳が改ざんされていない」ことを**誰でも検証できる**公開整合性
- 本人（と、本人が同意して渡した相手＝税理士・当局等）だけが中身を復号できる**view-key**

**作らない（❌）**
- 運営がユーザー資金を保管する口座（custodial balance）
- 見知らぬ第三者間の資金を混合する匿名プール／ミキサー
- KYCを回避するための匿名入出金経路
- 送金相手や金額の“出所隠し”を目的とした機能

## 2. アーキテクチャ（ノンカストディ3層）

```
┌─────────────────────────────────────────────────────────┐
│ Layer 1 : MORM L1（自己保管の決済・検証層）               │
│   - ユーザー口座は本人の署名鍵で支配（運営は動かせない）    │
│   - 残高/金額はコミットメント（Pedersen）で秘匿            │
│   - 有効性は zk / レンジ証明で検証（金額を晒さず二重支払防止）│
│   実体: morm-chain（既存 morm-l1.service を拡張）          │
└─────────────────────────────────────────────────────────┘
              ▲ 参照（read-only）
┌─────────────────────────────────────────────────────────┐
│ Layer 2 : クライアント側鍵・状態（ユーザー端末）           │
│   - 秘密鍵・view-key は端末内（運営に渡らない）            │
│   - 自分の履歴を view-key でローカル復号・表示             │
│   実体: MORM ウォレット（`/my` はここに接続）              │
└─────────────────────────────────────────────────────────┘
              ▲ deposit / ▼ withdraw（非預かり）
┌─────────────────────────────────────────────────────────┐
│ Layer 3 : 外部チェーン橋渡し（BTC/USDT ↔ MORM）           │
│   - ★最難関。custodian を置かずに繋ぐ（§5）               │
│   実体: atomic swap / HTLC / 分散ブリッジ（要方式決定）    │
└─────────────────────────────────────────────────────────┘
```

**v0.1 との差**：Turso は「真実の源（custody台帳）」ではなくなる。
真実は **L1のコミットメント＋ユーザー端末の鍵**にあり、Turso は任意の**公開インデクサ/キャッシュ**に降格（無くても資産は動く）。

## 3. 鍵設計

| 鍵 | 所有者 | 権限 | 備考 |
|---|---|---|---|
| **spend-key** | ユーザー本人のみ | 資産の移動（署名） | 運営は保持しない・複製しない |
| **view-key** | ユーザー本人 | 自分の残高/履歴の復号（読取専用） | 本人が任意で第三者（税理士・当局）に**選択的開示**可 |
| — audit-key（運営） | **無し** | — | ノンカストディゆえ運営に開示鍵は存在しない |

- 「当局への説明」は**運営のaudit-keyではなく、本人のview-key選択開示**で行う（＝Zcashのviewing key思想）。
- 運営は資金も開示鍵も持たない＝**単一障害点も没収対象も無い**。これがコンセプト優先の実利。

## 4. プライバシー実装（段階導入・すべて先行技術ベース §7）

1. **【Phase1】ステルスアドレス＋view-key**
   - 受取毎にワンタイムアドレスを導出（相手・第三者に受取を紐付けさせない）
   - 本人は view-key で自分宛を検出・復号。**まずここ**。
2. **【Phase2】Confidential Amounts**
   - Pedersen commitment ＋ **Bulletproofs**（trusted setup 不要）で金額秘匿・非負・収支一致を証明
3. **【Phase3】zk 状態証明**
   - 取引の有効性を zk-SNARK/STARK で証明。強力。回路コスト大、将来。

> 各Phaseとも **対象は「本人の自己保管資産」**。他人資産の匿名化リンク切断は実装しない（§0の一線）。

---

## 5. 外部チェーン橋渡し（最難関・要方式決定）

ノンカストディで BTC/USDT ↔ MORM を繋ぐのは本仕様最大の技術課題。custodian を置いた瞬間コンセプトが崩れる。候補：

| 方式 | ノンカストディ度 | 難度/課題 |
|---|---|---|
| **Atomic Swap (HTLC)** | ◎ 完全非預かり | 相手方流動性・UX・BTCスクリプト制約 |
| **分散ブリッジ（しきい値署名の非中央フェデレーション）** | △ 半信頼 | フェデレーション＝実質custody寄り。原則と緊張 |
| **DEX的P2Pマッチング（MORM↔外部を注文板で相対）** | ○ | 流動性ブートストラップ |

> **推奨検討順**：Atomic Swap を第一候補に据える。フェデレーション型は「法人を持たない／預からない」と緊張するため慎重に。
> ここで安易に custodian を置くと v0.1（VASP必要）に逆戻りする点に留意。

## 6. コンプラの考え方（ノンカストディ版）

custodial ではないため VASP 登録は原則不要だが、**免罪符ではない**。以下を守る：

- **§0の一線を絶対に越えない**（他人資金の混合＝mixer化しない）。越えた瞬間 Tornado Cash 相当のリスク。
- **本人主導の開示**：本人が view-key で税務・当局に説明できる導線を用意（運営が代わりに開示はできない/しない）。
- **オン/オフランプ（法定通貨接点）を自前で持たない**：法定通貨↔暗号資産は登録済み外部事業者に委ねる。ここを内製すると資金決済法に触れる。
- **先行技術の尊重・明示引用**（§7）。新規性の過大主張をしない（原則①）。

> 判定基準（ノンカストディ版）：**「運営は資金を保管せず、他人の資金を混合せず、法定通貨接点を内製しないか？」**
> すべてYesなら概ね正規。1つでもNoなら custodial/mixer/money-transmitter の壁に触れる。

※法的評価は管轄・実装で変わる。本番前に暗号資産に詳しい弁護士のレビュー必須（本仕様は設計指針であり法的助言ではない）。

## 7. 先行技術の認知（MORM原則①）

本設計は以下の既存研究・実装に依拠する。MORMは発明者を名乗らない。

- **ステルスアドレス**（CryptoNote / Monero）
- **Viewing key による選択的開示**（Zcash Sapling）
- **Pedersen commitment ＋ Bulletproofs**（Confidential Transactions / range proof, trusted-setup free）
- **zk-SNARK / STARK**（有効性証明）
- **Atomic Swap / HTLC**（非預かりクロスチェーン）

---

## 8. 実装ロードマップ（PoC）

- [ ] **P1**: MORMアカウント種から spend-key / view-key を BIP32 的に導出（鍵は端末内）
- [ ] **P2**: ステルスアドレス受取＋view-key検出をウォレットに実装
- [ ] **P3**: L1にコミットメント anchor、公開エクスプローラは commitment のみ、`/my` は view-key ローカル復号
- [ ] **P4**: Bulletproofs で金額秘匿（Confidential Amounts）
- [ ] **P5（橋）**: Atomic Swap PoC（MORM↔BTC 少額で）
- [ ] 各段階で「§0の一線を越えていないか」レビュー

**最初は P1〜P3**（自己保管鍵＋ステルス受取＋機密残高の本人ビュー）。ここまでで中核が動く。
